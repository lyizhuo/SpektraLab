# 增益图（HDR gain map）调研记录

写给要拍板的人：现状是什么、卡在哪、有几条路、每条路要多少、需要你定什么。

不是实现文档——这一项没有实现。下面每一条"不能"都有可复查的证据，
每一条"能"都标了是不是验证过。

---

## 1. 增益图到底要交付什么

一张 HDR 增益图不是一个"更亮的版本"，而是**在同一份文件里同时携带两个渲染结果**，
并告诉读图端怎么在两者之间插值：

- 一个 **SDR 基准**（现在的 10-bit HEIC 就是它）；
- 一张**低分辨率的增益图**，每个像素记录"要比基准亮多少倍"；
- 一段 **ISO 21496-1 元数据**，描述余量：基准能表示到多少、增益后能到多少、
  最小增益、gamma。

读图端按自己显示器的能力在两端之间取一个点，所以同一份文件在 SDR 屏上是现在的样子，
在 HDR 屏上多出高光。**基准不变得更亮**，这才是它和"直接导出更亮的图"的区别。

### 容器层的三样东西

在 HEIF 里它由这些组成，缺一不可：

1. 一张**辅助图像**（auxiliary image），带 `tmap` 的 item 引用关系；
2. 该辅助图像的类型断言，Apple 用 `urn:com:apple:photo:2020:aux:hdrgainmap`，
   ISO 用 `urn:iso:std:iso:ts:21496:-1`；
3. 上面那份元数据属性。

（Google 的 Ultra HDR 是同一套数据的 **JPEG** 版本，走 APP 段，不适用于我们的 HEIC。）

## 2. 现状：库写不出来

**这是硬事实，不是判断。**

HDR 增益图的写入入口全在 libheif 的 `heif_aux_images.h`。我们钉住的 **1.23.7**
里，这个头文件只有读接口：

```
heif_image_handle_get_number_of_auxiliary_images
heif_image_handle_get_list_of_auxiliary_image_IDs
heif_image_handle_get_auxiliary_type
heif_image_handle_release_auxiliary_type
heif_image_handle_get_auxiliary_image_handle
```

没有 `heif_context_encode_auxiliary_image`，没有 `heif_image_handle_set_auxiliary_type`。
把 `libheif/*.h` 全部 grep `21496`、`gain_map`、`gainmap`、`tmap`，**零命中**。

**并且这不是版本问题。** 拉了 upstream `master` 的同一个头文件（7,258 字节）核对，
仍然是只有读接口。所以"等一个新版本就好"目前不成立。

换句话说：libheif 能**读出**带增益图的文件，**写不出来**。我们只用它写。

**已经验证能写的**（本仓库实测，见 `HEIC-NOTES.md`）：10-bit HEVC、`heix` 主品牌、
ICC 逐字节嵌入、走 `colr`/`prof` 而不是 nclx 枚举。也就是说"基准"这一半是好的，
缺的是"第二份 + 元数据"这一半。

## 3. 关键一点：这份数据我们已经有了，而且正在扔掉

直觉上会说"胶片模拟没有 HDR 版本，增益图里没东西可放"。**这句话是错的。**

引擎输出的目标空间线性值**会超过 1.0**（`transform.to_linear` 之后、编码之前）。
编码器把它们压到容器天花板，那就是损失的那部分光。

而 `GamutReport` 的 `clipped` 计数，精确地等于**超过 1.0 的像素数**——
导出面板现在就把这个比率印在尺寸行下面：

```
超出目标色域 1.8% · 被映射 0.6% · 被夹限 0.1%
                              ^^^^^^ 这一项就是增益图的内容
```

所以产品上的说法是成立的：**ProPhoto 导出里被夹限的那一部分，就是 HDR 显示器能救回来的那部分照片。**

需要说明的边界：我**没有**记录过任何一张具体照片的 `clipped` 百分比。
这个数字按帧变化（取决于场景和色彩空间），面板会算，但仓库里没有一份"典型值"的测量。
做方案之前应该先测一批，否则"值不值得做"是拍脑袋。

## 4. 三条路，各自的代价和风险

### 路线 A：换一个能写辅助图像的库

**代价**：小，如果存在这样的库。
**风险**：libheif 是这个领域事实上的唯一选择；替代品（如写 HEIF 的轻量 muxer）
要么不成熟，要么同样不写 aux。需要先做一轮调研，我没有做。

**要确认的**：目标库是否真的支持 `tmap` + aux 类型断言 + 21496-1 元数据三件套，
而不是只支持"多图层"。

### 路线 B：patch libheif 的容器写入

**代价**：中到大。要在它的 item/property 写入层加一条路径，
并且保持和行为良好的读端兼容。
**风险**：这是 C++ 容器写入器，改错了产出的是"能打开但 HDR 端不认"的文件——
比直接失败更难查。

我们已经在 `android/scripts/build-heif.ps1` 里从源码编 libheif，
所以"打补丁"这件事在工程上是通的路，问题是要不要维护一个 fork。

### 路线 C：自己在 libheif 的输出上追加

**代价**：中。libheif 产出 ISO-BMFF 树之后，再补一个 item 和它的元数据。
**风险**：需要自己维护 `meta` box 的偏移和 `iloc` 索引；追加错了文件就是坏的。
好处是不改第三方代码，坏处是我们成了自己容器写入器的一部分实现者。

### 路线 D：先不做

不是凑数选项。**现在的导出已经把信息告诉用户了**（"被夹限 X%"），
增益图是"再多给一点"，不是"修一个错"。如果目标用户的观看端绝大多数是 SDR 屏，
这条路的收益接近零。

---

## 5. 需要你拍的四件事

1. **走哪条路**：A / B / C / D。我没有任何一条能在没有你的情况下选——
   它们的差别是"维护一个 fork"和"接受一个不完美"之间的取舍，是产品取舍。
2. **余量目标**：增益到 SDR 之上多少 stop？这是调色决定。
   没有这个数字，增益图无从计算——它不是"越亮越好"，是一个声明的上限。
3. **谁必须看到**：Apple 相册 / Google 相册 / 我们的 App 自己？
   这决定了用 Apple 的 URN 还是 ISO 的，以及要不要同时写两份断言。
4. **SDR 基准是否保持现状**：我建议保持——增益图的意义就是不动基准。

---

## 6. 如果做，怎么验

不能只看"文件能打开"。至少要：

- 用 libheif **读回**我们写的文件，确认能列出那张辅助图像、类型断言正确、
  元数据字段齐全（读端我们已经有了，正好当独立验证）；
- 把它和同一帧的 SDR 导出做像素比对：**基准必须逐像素不变**，
  否则就退化成"整体提亮"，那是另一种东西；
- 在一台真 HDR 设备上确认 SDR/HDR 两种显示模式下观感符合预期——这一条
  模拟器做不到，必须真机。

---

## 7. 一句话结论

技术上卡在一个明确的缺口（libheif 不写辅助图像，版本和上游都没有），
产品上卡在一个需要你给的数字（余量多少 stop）。
数据本身是有的，就在现在的导出里被夹掉。
